- One user REQUESTS the lock, another APPROVES it (with appropriate role).

   Example (you can adapt):

   - Add fields to payroll_periods and/or a separate dual_auth_requests table to track:
     - requestedBy, requestedAt
     - approvedBy, approvedAt
     - status: "lock_requested", "lock_approved"
   - Prevent the same user from being both requestedBy and approvedBy.

2) Update the lock/unlock flows so that:

   - A lock request:
     - Records that user A has requested the lock for period X.
   - A lock approval:
     - Requires user B with manager/admin-level role.
     - Validates user B != user A.
     - Only then sets status to "locked".
   - Unlock logic should also respect SoD constraints as appropriate (e.g. manager-level).

3) Enforce role checks based on existing role/permission system:
   - Only manager/admin/super_admin/owner-level roles should be able to approve locks and unlocks.
